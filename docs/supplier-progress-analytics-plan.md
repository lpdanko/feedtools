# План: аналитика прогресса по поставщикам

Дата фиксации: 2026-05-17

Статус: широкий черновик. Актуальная ограниченная версия для ближайшей реализации зафиксирована в `docs/supplier-content-progress-plan.md`.

## 1. Зачем нужен блок

Новый блок должен отвечать на четыре управленческих вопроса:

1. С какими поставщиками сейчас нужно работать в первую очередь.
2. Что именно мешает довести товары поставщика до продаж на маркетплейсах.
3. Как изменился прогресс за выбранный период.
4. Какой вклад в этот прогресс внес каждый пользователь FeedTools.

Это не просто отчет по текущему состоянию. Нужна система оценок, исторических слепков, событий прогресса и пользовательского вклада.

## 2. Текущий контекст проекта

В проекте уже есть база, на которую можно опереться:

1. Поставщики:
   - `feedtools_suppliers`
   - `feedtools_supplier_product_meta`
   - `feedtools_supplier_products`
   - `feedtools_supplier_product_fields`

2. Маркетплейсные состояния:
   - `feedtools_ozon_products`: статус, архив, ошибки, модерация, validation, content rating.
   - `feedtools_wb_products`: статус, активность, quality score, рекомендации, архив.

3. Операции и пользователи:
   - `feedtools_operations.created_by`
   - `feedtools_operations.summary_json`
   - `feedtools_operations.progress_*`
   - текущий пользователь берется через `ft_current_user()` / basic auth.

4. Уже есть админская аналитика сотрудников:
   - `app/employee_analytics.php`
   - `public/staff_analytics.php`

Вывод: новый функционал стоит строить отдельным слоем поверх текущих таблиц, не ломая существующие страницы поставщиков и операций.

## 3. Основные сущности новой системы

### 3.1. Поставщик

Поставщик является главным объектом дашборда. Для него считаются:

1. Общий прогресс.
2. Прогресс по каждому маркетплейсу.
3. Проблемы и исправимые ошибки.
4. Качество карточек.
5. Коммерческая готовность.
6. Динамика за период.
7. Вклад пользователей.

### 3.2. Товар поставщика

Товар поставщика является атомарной единицей оценки. Базовая строка берется из `feedtools_supplier_products`.

Нужно нормализовать несколько идентификаторов:

1. `product_id`: внутренний id из `feedtools_supplier_products.id`.
2. `supplier_id`: поставщик.
3. `offer_id`: артикул/offer id.
4. `vendor_code`: код товара, который используется для WB.
5. `marketplace`: `ozon`, `wb`, позже `yandex`.
6. `connection_id`: кабинет маркетплейса, если статус зависит от подключения.

### 3.3. Состояние товара на маркетплейсе

У каждого товара по каждому маркетплейсу должен быть нормализованный статус:

1. `not_created`: товара нет на маркетплейсе.
2. `draft_ready`: товар подготовлен в FeedTools, но еще не отправлен.
3. `pushed`: товар отправлялся на маркетплейс, но финальный статус еще не подтвержден.
4. `revision`: карточка на доработке.
5. `error`: есть ошибка создания, обновления, валидации или объединения.
6. `ready`: карточка принята и готова.
7. `sellable`: карточка реально может продаваться: есть валидный статус, цена и остаток.
8. `archived`: товар в архиве.

### 3.4. Проблема товара

Проблемы нужно хранить не только текстом, а типизированно:

1. `missing_marketplace_category`: не выбрана категория Ozon/WB.
2. `missing_required_attribute`: не заполнена обязательная характеристика.
3. `invalid_attribute`: характеристика не проходит маркетплейс.
4. `missing_brand`: нет бренда или бренд не сопоставлен.
5. `brand_rejected`: бренд не принят маркетплейсом.
6. `missing_title`: нет названия.
7. `weak_title`: название требует улучшения.
8. `missing_description`: нет описания.
9. `weak_description`: описание короткое/плохое.
10. `missing_images`: нет фото.
11. `weak_images`: мало фото или есть водяные знаки.
12. `missing_dimensions`: нет габаритов/веса.
13. `missing_price`: нет цены.
14. `missing_stock`: нет остатка.
15. `marketplace_validation_error`: ошибка валидации маркетплейса.
16. `moderation_revision`: карточка на доработке.
17. `marketplace_archive`: товар в архиве.
18. `duplicate_or_merge_error`: ошибка объединения/дубля.

Каждая проблема получает:

1. `severity`: `critical`, `major`, `minor`, `improvement`.
2. `fixability`: `auto`, `semi_auto`, `manual`, `external`.
3. `marketplace`: `ozon`, `wb`, `all`.
4. `effort`: оценка 1-5.
5. `impact`: оценка 1-5.

## 4. Система оценок

### 4.1. Общий прогресс поставщика

`progress_score` от 0 до 100.

Предлагаемые веса:

1. Coverage, 35 баллов: сколько товаров поставщика уже заведено на маркетплейсы.
   - Ozon coverage.
   - WB coverage.
   - доля товаров, которые есть хотя бы на одном маркетплейсе.
   - доля товаров, которые есть на всех целевых маркетплейсах.

2. Readiness, 20 баллов: насколько товары готовы к отправке.
   - есть категории.
   - есть обязательные характеристики.
   - есть бренд.
   - есть цена.
   - есть остаток.
   - есть фото.

3. Content quality, 20 баллов: качество карточек.
   - Ozon content rating.
   - WB quality score.
   - полнота описания.
   - качество названий.
   - количество фото.
   - rich content/описательные блоки, если появятся.

4. Error health, 15 баллов: насколько мало ошибок.
   - карточки без ошибок валидации.
   - нет массовых ошибок объединения.
   - нет карточек на доработке.
   - нет критичных фатальных блокеров.

5. Commercial activation, 10 баллов: насколько товары реально продаваемые.
   - товар активен на маркетплейсе.
   - есть цена.
   - есть остаток.
   - не архив.
   - не скрыт.

### 4.2. Индекс приоритета работы

`work_priority_score` от 0 до 100, где больше значит "этого поставщика нужно брать раньше".

Факторы:

1. Потенциал незаведенных товаров:
   - много товаров поставщика еще не добавлено на маркетплейсы.
   - поставщик активен.
   - есть остатки.

2. Быстрые победы:
   - много исправимых авто/полуавто ошибок.
   - ошибки типовые: категории, бренды, характеристики, заголовки.

3. Бизнес-эффект:
   - много товаров с остатком.
   - товары уже частично готовы.
   - после исправления товар может стать `sellable`.

4. Стагнация:
   - за последние периоды нет прогресса.
   - ошибки копятся.
   - упал quality score.

5. Риск:
   - растет количество ошибок.
   - много карточек ушло в архив/доработку.
   - большой откат по sellable count.

### 4.3. Индекс быстрых побед

`quick_win_score` от 0 до 100.

Цель: показать, где небольшое действие даст большой прирост.

Примеры:

1. 200 товаров без WB-категории, но Ozon-категория уже есть.
2. 150 товаров с отсутствующим брендом, бренд можно сопоставить словарем.
3. 80 товаров с ошибкой обязательной характеристики, значение есть в исходных параметрах.
4. 50 товаров не продаются только из-за нулевого остатка.

### 4.4. Индекс риска

`risk_score` от 0 до 100.

Факторы:

1. Рост ошибок за период.
2. Падение количества sellable товаров.
3. Массовая модерация/доработка.
4. Много карточек с одинаковой ошибкой.
5. Старый импорт поставщика.
6. Старые статусы маркетплейса.

## 5. Историческая модель

### 5.1. Почему нужны слепки

Текущие таблицы показывают только состояние "сейчас". Для сравнения периодов нужно хранить историю:

1. сколько было товаров в начале периода;
2. сколько стало в конце;
3. какие ошибки появились;
4. какие ошибки исчезли;
5. сколько товаров перешло в `ready` / `sellable`;
6. кто сделал действия, которые привели к изменениям.

### 6.2. Источники для assessment

Для каждого товара поставщика собрать:

1. Из `feedtools_supplier_products`:
   - название.
   - бренд.
   - категории Ozon/WB.
   - описание.
   - цена.
   - остаток.
   - фото.
   - параметры.
   - габариты/вес из standard fields.

2. Из `feedtools_supplier_product_fields`:
   - стандартные поля.
   - характеристики.
   - фишки.
   - marketplace-specific значения.

3. Из Ozon:
   - `feedtools_ozon_products` по `connection_id + offer_id`.
   - `marketplace_status`.
   - `status_name`.
   - `status_failed`.
   - `moderate_status`.
   - `validation_status`.
   - `content_rating`.

4. Из WB:
   - `feedtools_wb_products` по `connection_id + vendor_code`.
   - `marketplace_status`.
   - `status_text`.
   - `quality_score`.
   - `quality_recommendations_json`.

5. Из операций:
   - последние операции по dataset поставщика.
   - `created_by`.
   - `summary_json`.

### 6.3. Нормализация статусов

Для Ozon:

1. `is_archived = 1` -> `archived`.
2. validation/moderation failed -> `error` или `revision`.
3. active + status ok -> `ready`.
4. not found -> `not_created`.
5. ready + price + stock -> `sellable`.

Для WB:

1. `is_trash = 1` -> `archived`.
2. `marketplace_status = error` -> `error`.
3. `marketplace_status = revision` -> `revision`.
4. active/ready -> `ready`.
5. not found -> `not_created`.
6. ready + price + stock -> `sellable`.

### 6.4. Нормализация проблем

Сначала считаем базовые проблемы без сложной taxonomy:

1. Нет категории Ozon/WB.
2. Нет бренда.
3. Нет фото.
4. Нет цены.
5. Нет остатка.
6. Нет описания.
7. Слишком короткое название.
8. Нет габаритов/веса.
9. Ошибка маркетплейса.
10. Модерация/доработка.
11. Архив.

Потом добавляем более точные проблемы:

1. обязательные характеристики по taxonomy;
2. некорректные значения справочников;
3. проблемы бренда по словарям маркетплейсов;
4. рекомендации WB;
5. Ozon content rating рекомендации, если будут доступны в raw_json.

## 9. Мониторинг прогресса за период

### 9.1. Периодный отчет

Можно встроить в `supplier_progress.php` или сделать отдельную страницу:

`public/supplier_progress_period.php`

Сравнение:

1. период `A`: выбранный период;
2. период `B`: предыдущий равный период;
3. snapshot на начало и конец;
4. события внутри периода.

### 9.2. Метрики периода

По поставщику:

1. `products_total_delta`: стало больше/меньше товаров в источнике.
2. `marketplace_created_delta`: добавлено на маркетплейсы.
3. `ready_delta`: прирост готовых карточек.
4. `sellable_delta`: прирост реально продаваемых товаров.
5. `errors_delta`: изменение количества ошибок.
6. `issues_resolved`: исправлено проблем.
7. `critical_issues_resolved`: исправлено критичных проблем.
8. `quality_score_delta`: изменение качества.
9. `progress_score_delta`: изменение общего прогресса.
10. `work_priority_delta`: поставщик стал более/менее срочным.

### 9.3. Представления

1. Топ поставщиков по приросту.
2. Топ поставщиков по регрессу.
3. Топ поставщиков по исправленным ошибкам.
4. Топ поставщиков по добавленным товарам.
5. Топ поставщиков с застоем.
6. Топ быстрых побед на следующий период.

### 9.4. Waterfall/разложение прогресса

Для каждого поставщика:

1. Начальный score.
2. Плюс: добавлены товары на маркетплейсы.
3. Плюс: исправлены ошибки.
4. Плюс: улучшено качество.
5. Плюс: товары стали sellable.
6. Минус: появились новые ошибки.
7. Минус: товары ушли в архив/доработку.
8. Финальный score.

## 10. Вклад пользователей

### 10.1. Принцип атрибуции

Основной источник: `feedtools_operations.created_by`.

Правила:

1. Если пользователь запустил операцию, улучшения от операции относятся к нему.
2. Если операция системная/cron, actor = `system` или `automation`.
3. Если операция является дочерним шагом pipeline, actor наследуется от root operation.
4. Если изменение сделано ручным row action, actor берется из `ft_current_user()`.
5. Если статус улучшился после sync marketplace, но sync запущен пользователем, ему можно засчитать "подтвержденный результат", но отдельно пометить как marketplace-confirmed.

### 10.2. Что считать вкладом

Считать не только запуски, а реальные улучшения:

1. Товар добавлен на маркетплейс.
2. Товар стал ready.
3. Товар стал sellable.
4. Ошибка исправлена.
5. Критичная проблема исправлена.
6. Добавлена категория.
7. Добавлен бренд.
8. Заполнена обязательная характеристика.
9. Улучшено название.
10. Улучшено описание.
11. Добавлены/исправлены фото.
12. Увеличился quality score.

### 10.3. Баллы вклада

`impact_points` для события:

1. `status_became_sellable`: 10.
2. `status_became_ready`: 7.
3. `product_added_to_marketplace`: 6.
4. `critical_issue_resolved`: 5.
5. `required_attr_filled`: 4.
6. `category_assigned`: 4.
7. `brand_assigned`: 3.
8. `title_improved`: 2.
9. `description_improved`: 2.
10. `photo_improved`: 2.
11. `minor_issue_resolved`: 1.
12. `status_regressed`: negative points.

Важно: баллы нужны для сравнения вклада, а не для зарплатной метрики. В UI нужно показывать и raw metrics, и impact points.

### 10.4. Пользовательский отчет

В периодном отчете:

1. Пользователь.
2. Поставщиков затронуто.
3. Товаров обработано.

## 14. Важные продуктовые решения

### 14.1. Два разных score

Нельзя смешивать "поставщик хороший" и "с ним нужно работать".

1. `progress_score`: насколько поставщик готов.
2. `work_priority_score`: насколько срочно им заняться.

Поставщик может иметь низкий progress, но низкий priority, если у него мало товаров или проблемы не исправимы сейчас. И наоборот: поставщик с неплохим progress может иметь высокий priority, если у него много быстрых побед.

### 14.2. Считать sellable отдельно

Добавленный на маркетплейс товар еще не равен продающемуся товару.

Нужны отдельные числа:

1. `created_total`
2. `ready_total`
3. `sellable_total`

### 14.3. Ошибки должны быть типизированы

Текст ошибки нужен как пояснение, но управление должно идти по кодам проблем. Иначе невозможно строить аналитику "сколько исправимых ошибок по поставщику".

### 14.4. Пользовательский вклад должен быть результатом, а не активностью

Запуск операции сам по себе не равен прогрессу. Вклад пользователя нужно считать по изменениям состояния товаров и исправленным проблемам.

## 16. Усиление концепции: от аналитики к операционной системе

Базовый план уже дает диагностику. Чтобы сделать функционал сильнее, нужно добавить управленческий контур: цель, очередь работ, следующее действие, владелец, дедлайн, результат, ретроспектива.

### 16.1. Поставщик как рабочий поток

Для каждого поставщика полезно вести не только score, а стадию работы:

1. `new`: поставщик добавлен, товары еще не разобраны.
2. `catalog_imported`: товары загружены в FeedTools.
3. `mapping`: идет сопоставление категорий, брендов, характеристик.
4. `content_enrichment`: улучшаются названия, описания, фото, параметры.
5. `marketplace_push`: товары активно отправляются на маркетплейсы.
6. `moderation_fix`: исправляются ошибки и доработки.
7. `activation`: доводим товары до sellable: цена, остаток, активность.
8. `maintenance`: поставщик в поддержке, мониторим регрессы.
9. `blocked`: работа заблокирована внешней причиной.

Это даст более понятный управленческий вопрос: не только "какой score", но и "на каком этапе застрял поставщик".

### 16.2. План поставщика

Добавить сущность "план работ по поставщику":

`feedtools_supplier_work_plans`

Поля:

1. `id`
2. `supplier_id`
3. `status`: `open`, `in_progress`, `done`, `paused`
4. `owner_user`
5. `target_date`
6. `target_progress_score`
7. `target_sellable_total`
8. `target_marketplaces_json`
9. `notes`
10. `created_at`
11. `updated_at`

План нужен, чтобы аналитика сравнивала факт не только с прошлым периодом, но и с целью.

Пример:

1. За 14 дней довести поставщика до `progress_score >= 75`.
2. Добавить на Ozon минимум 400 товаров.
3. Довести до sellable минимум 250 товаров.
4. Исправить все critical issues.

### 16.3. Задачи и очередь работ

Добавить задачи, которые система генерирует автоматически:

`feedtools_supplier_work_items`

Поля:

1. `id`
2. `supplier_id`
3. `marketplace`
4. `issue_code`
5. `title`
6. `description`
7. `status`: `open`, `assigned`, `in_progress`, `done`, `dismissed`, `blocked`
8. `priority`
9. `expected_impact_points`
10. `expected_products_count`
11. `fixability`
12. `owner_user`
13. `source_snapshot_id`
14. `created_by`: `system` или пользователь
15. `created_at`
16. `due_at`
17. `closed_at`

Задачи должны группировать однотипные проблемы:

1. "Назначить WB-категорию для 186 товаров".
2. "Заполнить бренд для 74 товаров".
3. "Исправить ошибку объединения Ozon для 32 товаров".
4. "Добавить фото для 41 товара".
5. "Вернуть остатки для 119 товаров, которые готовы, но не sellable".

Главная ценность: контент-менеджер не изучает весь дашборд каждый раз, а открывает свою очередь.

### 16.4. Next Best Action

Для каждого поставщика система должна показывать одно главное следующее действие.

Алгоритм:

1. Собрать все issue groups.
2. Оценить `impact`: сколько товаров станут ready/sellable или насколько вырастет score.
3. Оценить `effort`: насколько действие трудоемкое.
4. Оценить `confidence`: насколько система уверена, что действие сработает.
5. Оценить `dependency`: есть ли предварительные блокеры.
6. Рассчитать `action_score = impact * confidence / effort`.

Примеры next best action:

1. "Сначала назначить категории WB: это разблокирует 312 товаров".
2. "Сначала исправить бренды Ozon: 58 карточек уже почти готовы".
3. "Сначала обновить остатки: 140 товаров готовы, но не продаются".
4. "Сначала синхронизировать статусы Ozon: данные старше 3 дней, оценка ненадежна".

### 16.5. Уверенность в данных

Нужно добавить `data_confidence_score`.

Почему это важно: плохая аналитика хуже отсутствия аналитики. Если статусы маркетплейса устарели, score должен быть помечен как ненадежный.

Факторы:

1. Когда последний раз импортирован фид поставщика.
2. Когда последний раз синхронизированы Ozon товары.
3. Когда последний раз синхронизированы WB товары.
4. Есть ли connection_id для маркетплейсов.
5. Совпадают ли offer_id/vendor_code.
6. Есть ли подозрительно много `not_created`, вызванных не отсутствием товаров, а плохим matching.

UI должен явно показывать:

1. "Данные свежие".
2. "Статусы Ozon устарели".
3. "WB не синхронизирован".
4. "Низкая уверенность из-за проблем сопоставления артикулов".

### 16.6. Разделение причин: проблема данных, проблема карточки, проблема бизнеса

Ошибки нужно группировать по природе:

1. `data_problem`: FeedTools не знает нужных данных.
   - нет категории.
   - нет бренда.
   - нет характеристик.

2. `content_problem`: карточка слабая.
   - плохое название.
   - нет описания.
   - мало фото.

3. `marketplace_problem`: маркетплейс не принял товар.
   - ошибка валидации.
   - доработка.
   - архив.
   - ошибка объединения.

4. `commercial_problem`: товар не может продаваться.
   - нет цены.
   - нет остатка.
   - товар скрыт.

5. `process_problem`: проблема процесса.
   - давно не синхронизировали.
   - никто не взял в работу.
   - поставщик застрял в стадии.

Так руководитель сразу понимает, кому отдавать задачу: контенту, операционному менеджеру, разработке, закупке или маркетплейсному специалисту.

### 16.7. Прогноз результата

Добавить forecast:

1. `forecast_progress_after_quick_wins`
2. `forecast_sellable_after_quick_wins`
3. `forecast_days_to_target`
4. `forecast_blocked_products`

Пример в UI:

1. Сейчас progress 42.
2. После автоисправимых задач будет 61.
3. После ручных задач высокого приоритета будет 78.
4. До цели при текущем темпе: 9 рабочих дней.

Это превращает аналитику из "что плохо" в "что будет, если мы сделаем X".

### 16.8. SLA и старение проблем

У каждой проблемы и work item должен быть возраст:

1. `first_seen_at`
2. `last_seen_at`
3. `age_days`
4. `sla_status`: `ok`, `warning`, `overdue`

Правила:

1. Critical issue старше 2 рабочих дней: warning.
2. Critical issue старше 5 рабочих дней: overdue.
3. Поставщик без прогресса 7 дней: stalled.
4. Данные маркетплейса старше 3 дней: stale.

Это позволит видеть не только объем проблем, но и дисциплину процесса.

### 16.9. Регрессы как отдельный контур

Регресс важнее обычной ошибки, потому что он означает потерю уже достигнутого результата.

Отдельно показывать:

1. Товары были `sellable`, стали не sellable.
2. Товары были `ready`, ушли в error/revision.
3. Ошибки были исправлены, потом вернулись.
4. Quality score упал.
5. Поставщик потерял товары из источника.

Для регрессов нужны:

1. отдельный `regression_score`;
2. алерт на портфельной странице;
3. отдельный список "что сломалось за период".

### 16.10. Сегментация поставщиков

Все поставщики разные, поэтому единый score не должен быть единственным способом смотреть на портфель.

Добавить сегменты:

1. `high_volume`: много товаров.
2. `quick_win`: много исправимых проблем.
3. `blocked`: много внешних блокеров.
4. `almost_done`: высокий progress, осталось немного.
5. `stalled`: давно нет движения.
6. `risky`: растут ошибки/регрессы.
7. `maintenance`: все нормально, только мониторинг.

На портфельной странице должны быть вкладки или фильтры по сегментам.

### 16.11. Бенчмарки

Поставщика полезно сравнивать не только с собой, но и с похожими поставщиками.

Метрики:

1. Средний progress по всем поставщикам.
2. Средний progress по поставщикам похожего размера.
3. Median time to ready.
4. Median time to sellable.
5. Типичная доля ошибок по Ozon/WB.
6. Типичная доля товаров без категории/бренда/фото.

UI:

1. "Этот поставщик хуже медианы по WB coverage на 28 п.п."
2. "Ошибок объединения в 3.2 раза больше нормы".
3. "По quick wins поставщик в top 10%".

### 16.12. Качество работы пользователя

Вклад пользователя лучше мерить не только количеством действий.

Добавить метрики:

1. `impact_points`: полезный результат.
2. `first_pass_success_rate`: доля действий, после которых карточка не вернулась в ошибку.
3. `regression_caused_count`: сколько изменений привело к откату.
4. `critical_resolved_count`.
5. `sellable_created_count`.
6. `avg_time_to_resolve`.
7. `rework_rate`: сколько пришлось переделывать.

Так система не будет мотивировать просто массово запускать операции.

### 16.13. Объяснимость score

Каждый score должен иметь объяснение:

1. "Почему score такой?"
2. "Что сильнее всего снижает score?"
3. "Какой прирост даст следующее действие?"
4. "Какие данные устарели?"
5. "Почему поставщик в приоритете?"

В БД это хранить как:

1. `score_breakdown_json`
2. `priority_reasons_json`
3. `recommended_actions_json`
4. `data_warnings_json`

### 16.14. Режимы просмотра

Для разных ролей нужны разные режимы:

1. Руководитель:
   - портфель;
   - приоритеты;
   - прогресс за период;
   - вклад пользователей;
   - регрессы.

2. Контент-менеджер:
   - моя очередь;
   - задачи по поставщикам;
   - товары, которые можно быстро исправить;
   - результат моей работы.

3. Маркетплейс-специалист:
   - ошибки Ozon/WB;
   - модерация;
   - архив;
   - статусы синхронизации.

4. Операционный менеджер:
   - остатки;
   - цены;
   - sellable;
   - коммерческая активация.

Даже если роли пока не формализованы в auth, структура UI должна быть готова к этому.

### 16.15. Лучший MVP после усиления

MVP можно сделать сильнее без чрезмерного усложнения:

1. Сразу добавить `data_confidence_score`.
2. Сразу добавить `next_best_action`.
3. Сразу хранить `priority_reasons_json`.
4. Сразу группировать проблемы по природе: data/content/marketplace/commercial/process.
5. Сразу считать `regression_count` за период.
6. Сразу сделать простую очередь work items, хотя бы read-only.

Это даст продукту ощущение умной системы уже в первой версии.

## 17. Второй слой усилений: экономика, прогноз, контроль качества и масштабирование

Раздел 16 превращает дашборд в рабочую систему. Следующий слой должен сделать ее управленчески зрелой: считать не только прогресс, но и экономический эффект, стоимость работы, надежность данных, качество решений и масштабируемость команды.

### 17.1. Opportunity score: экономический потенциал поставщика

`work_priority_score` отвечает на вопрос "где работать". Но руководителю нужен еще вопрос "зачем именно там работать с точки зрения денег".

Добавить `opportunity_score` от 0 до 100.

Факторы:

1. Сколько товаров поставщика имеют остаток.
2. Сколько товаров почти готовы стать sellable.
3. Потенциальная выручка по товарам:
   - цена;
   - остаток;
   - marketplace coverage;
   - исторические продажи, если позже подключить заказы.
4. Потенциальная маржа, если есть закупочная цена.
5. Дефицит покрытия:
   - товары есть у поставщика, но их нет на Ozon/WB.
6. Скорость доведения до продажи:
   - quick wins;
   - доля автоисправимых проблем.

Формула первого приближения:

`opportunity_score = normalized(stock_value_unlisted + stock_value_not_sellable + quick_win_value)`

Где:

1. `stock_value_unlisted` = сумма `price * stock` по товарам, которых нет на маркетплейсе.
2. `stock_value_not_sellable` = сумма `price * stock` по товарам, которые заведены, но не продаются.
3. `quick_win_value` = сумма потенциала товаров с авто/полуавто исправлениями.

### 17.2. Expected Value и ROI задач

Для каждой work item полезно считать ожидаемую ценность:

1. `expected_products_unblocked`
2. `expected_sellable_delta`
3. `expected_stock_value_unblocked`
4. `expected_revenue_proxy`
5. `expected_margin_proxy`
6. `estimated_effort_minutes`
7. `expected_value_per_hour`

Это позволит сортировать задачи не только по количеству товаров, но и по эффекту на бизнес.

Пример:

1. Задача A исправляет 200 товаров, но без остатков.
2. Задача B исправляет 30 товаров с большим остатком и высокой ценой.
3. По количеству A больше, по бизнес-эффекту B важнее.

### 17.3. Capacity planning: планирование мощности команды

Нужна модель "сколько работы может выполнить команда".

Метрики:

1. Сколько impact points делает пользователь в день/неделю.
2. Сколько critical issues закрывает пользователь.
3. Сколько товаров доводит до ready/sellable.
4. Среднее время закрытия типовой задачи:
   - категория;
   - бренд;
   - атрибуты;
   - фото;
   - модерация;
   - остатки/цены.
5. Пропускная способность команды по типам задач.

UI:

1. "Текущий backlog: 4300 минут работы".
2. "При текущей скорости команда закроет high-priority backlog за 9 рабочих дней".
3. "Узкое место: WB-категории".
4. "Нужно 1.5 FTE контент-менеджера, чтобы закрыть цель к дате".

### 17.4. Bottleneck analysis

Добавить отдельный блок "где бутылочное горлышко".

Возможные bottlenecks:

1. Категории Ozon/WB.
2. Бренды.
3. Обязательные характеристики.
4. Фото.
5. Описание/названия.
6. Ошибки маркетплейса.
7. Модерация.
8. Цены.
9. Остатки.
10. Несвежие статусы.
11. Нехватка людей на конкретном типе задач.

Система должна уметь сказать:

1. "70% непродаваемых товаров блокируются остатками".
2. "Главный blocker для WB: нет предмета у 43% товаров".
3. "Главный blocker для Ozon: ошибки бренда".
4. "Контент готов, но коммерческая активация отстает".

### 17.5. Dependency graph: зависимости между проблемами

Некоторые задачи бесполезно делать до предыдущих.

Примеры:

1. Нельзя валидно заполнить обязательные характеристики, пока не выбрана категория.
2. Нет смысла пушить товар, пока нет фото.
3. Нельзя считать sellable, пока не синхронизированы статусы.
4. Нельзя оценить brand rejection, пока бренд не отправлялся на marketplace.

Добавить dependency model:

1. `issue_code`
2. `depends_on_issue_codes`
3. `unblocks_issue_codes`
4. `stage`
5. `recommended_order`

Это улучшит next best action: система будет рекомендовать не самую большую проблему, а первую проблему в цепочке.

### 17.6. Versioned scoring: версии правил оценки

Scoring будет меняться. Если не версионировать правила, исторические графики станут нечестными.

Добавить:

1. `feedtools_supplier_scoring_versions`
2. `version_key`
3. `weights_json`
4. `rules_json`
5. `created_at`
6. `created_by`
7. `is_active`

В snapshots хранить:

1. `scoring_version_key`
2. `score_breakdown_json`

Для истории:

1. старые snapshots остаются со старой версией;
2. можно пересчитать историю новой версией отдельным rebuild;
3. UI должен показывать, если период сравнивается между разными версиями scoring.

### 17.7. Rule engine для проблем и score

Не стоит навсегда зашивать все правила в PHP-коде. На первом этапе можно кодом, но структура должна быть похожа на rule engine.

Правило должно описывать:

1. `rule_code`
2. `title`
3. `description`
4. `marketplace`
5. `condition`
6. `issue_code`
7. `severity`
8. `fixability`
9. `impact`
10. `effort`
11. `recommended_action_template`
12. `enabled`

Позже это позволит:

1. отключать спорные правила;
2. менять веса без релиза;
3. добавлять правила для конкретного marketplace;
4. объяснять пользователю, почему проблема обнаружена.

### 17.8. Quality control sampling

Нужен контроль качества результата, иначе пользователи могут "улучшать score", но ухудшать карточки.

Добавить выборочную проверку:

1. система выбирает N товаров после массовой операции;
2. показывает before/after;
3. руководитель или старший контент-менеджер ставит оценку;
4. оценка влияет на quality metrics пользователя и доверие к операции.

Таблица:

`feedtools_supplier_quality_reviews`

Поля:

1. `id`
2. `supplier_id`
3. `product_id`
4. `op_id`
5. `actor_user`
6. `reviewer_user`
7. `review_status`: `approved`, `needs_rework`, `rejected`
8. `review_score`
9. `comment`
10. `before_json`
11. `after_json`
12. `created_at`
13. `reviewed_at`

### 17.9. Rework loop: контур переделок

Если задача закрыта, но проблема вернулась, это нужно видеть.

Метрики:

1. `reopened_issues_count`
2. `rework_items_count`
3. `rework_rate`
4. `same_issue_returned_days`
5. `regression_after_user_action`

UI:

1. "Эта ошибка уже исправлялась 2 раза".
2. "После операции X 18 товаров снова вернулись в error".
3. "Типовая причина переделки: неверная категория".

### 17.10. Golden path playbooks

Для повторяющихся проблем нужны готовые сценарии исправления.

Примеры playbooks:

1. "Новый поставщик с нуля".
2. "Много товаров без WB-категорий".
3. "Ошибки бренда Ozon".
4. "Товары готовы, но не sellable из-за остатков".
5. "Много карточек на доработке".
6. "Поставщик застрял после импорта".

Каждый playbook:

1. условия применения;
2. список шагов;
3. автоматические операции FeedTools;
4. ручные проверки;
5. expected result;
6. fallback, если шаг не сработал.

Это можно показать как "рекомендуемый сценарий" на странице поставщика.

### 17.11. AI assistant внутри дашборда

Когда данных станет много, полезен встроенный помощник по поставщику.

Функции:

1. Краткое объяснение состояния поставщика.
2. Ответ на вопрос "почему progress упал?".
3. Ответ на вопрос "что сделать сегодня?".
4. Генерация плана работ на неделю.
5. Объяснение вклада пользователя.
6. Сводка по регрессам.
7. Генерация комментария для руководителя.

Важно: AI не должен быть источником истины. Он должен объяснять уже посчитанные факты из snapshots/events/issues.

### 17.12. Alert digest вместо шума

Уведомления должны быть агрегированными, иначе они быстро станут мусором.

Ежедневный digest:

1. Топ-5 поставщиков, где нужен фокус сегодня.
2. Новые критичные регрессы.
3. Поставщики без прогресса.
4. Просроченные critical issues.
5. Лучшие улучшения вчера.
6. Пользователи с заметным вкладом.

Еженедельный digest:

1. Прирост sellable.
2. Прирост marketplace coverage.
3. Закрытые critical issues.
4. Поставщики, достигшие цели.
5. Главные bottlenecks.
6. План на следующую неделю.

### 17.13. Supplier health timeline

Для каждого поставщика полезна лента здоровья:

1. импорт обновлен;
2. товаров стало больше/меньше;
3. score вырос/упал;
4. запущена операция;
5. исправлена массовая ошибка;
6. появился регресс;
7. поставщик перешел стадию;
8. изменился owner/plan.

Это помогает быстро понять историю без чтения логов.

### 17.14. Data lineage: откуда взялась цифра

Каждая важная цифра должна иметь происхождение.

Примеры:

1. "Ozon ready total: взято из `feedtools_ozon_products`, sync от 2026-05-17 01:12".
2. "WB quality score: взято из `feedtools_wb_products.raw_json`, sync от ...".
3. "Stock: взято из `feedtools_supplier_products.stock_qty`, импорт поставщика от ...".
4. "Issue missing_brand: правило `missing_brand_v1`, assessment от ...".

Это важно для доверия к системе и отладки.

### 17.15. Supplier ownership

Если пользователей будет несколько, нужен owner.

Добавить:

1. `owner_user` у поставщика или work plan.
2. `secondary_owner_user`, если нужен дублер.
3. `assigned_at`
4. `owner_notes`

UI:

1. Мои поставщики.
2. Поставщики без владельца.
3. Поставщики с просроченными задачами владельца.
4. Нагрузка по владельцам.

### 17.16. Роли и права

Сейчас auth простая, но функционал будет требовать ролей.

Минимальные роли:

1. `admin`: все.
2. `manager`: дашборды, планы, назначение задач.
3. `content`: свои задачи и товары.
4. `marketplace`: marketplace ошибки и статусы.
5. `viewer`: только просмотр.

Даже если роли внедрять позже, новые страницы не должны предполагать, что все пользователи равны.

### 17.17. Product family analytics

Оценивать нужно не только отдельные товары, но и группы:

1. категория поставщика;
2. бренд;
3. серия/модель;
4. комплекты;
5. похожие товары;
6. ценовой сегмент.

Польза:

1. увидеть, что проблема не у поставщика целиком, а у одной категории;
2. исправлять массово;
3. строить playbooks по группам;
4. оценивать прогресс не только "по штукам", но и по ассортиментным блокам.

### 17.18. Ассортиментные пробелы между маркетплейсами

Отдельная аналитика:

1. Есть на Ozon, нет на WB.
2. Есть на WB, нет на Ozon.
3. Есть на обоих, но sellable только на одном.
4. Разный quality score по площадкам.
5. Разные причины блокировки по площадкам.

Это даст конкретные задачи для расширения покрытия.

### 17.19. Исторические когорты

Смотреть поставщиков когортами:

1. добавлены в один месяц;
2. один размер;
3. одна категория;
4. один ответственный;
5. один источник;
6. один marketplace target.

Вопросы:

1. Сколько дней проходит от импорта до первых sellable товаров.
2. Где процесс стал быстрее.
3. Какие типы поставщиков сложнее.
4. Какие пользователи/команды быстрее доводят до результата.

### 17.20. Anomaly detection

Добавить простые аномалии:

1. Резко упало количество товаров.
2. Резко выросли ошибки.
3. Резко упал sellable.
4. Статусы давно не обновлялись.
5. Необычно много архивированных товаров.
6. Операция дала нетипично мало результата.
7. Пользователь закрыл много задач, но score не вырос.

На первом этапе это простые пороги, позже можно сделать статистические правила.

### 17.21. Управление целями: OKR/targets

Для команды полезны цели:

1. За неделю добавить 1000 товаров на Ozon.
2. Довести 600 товаров до sellable.
3. Снизить critical issues на 40%.
4. Довести 10 поставщиков до progress 80+.
5. Закрыть все stale sync.

Таблица:

`feedtools_supplier_progress_targets`

Поля:

1. `id`
2. `target_type`
3. `scope`: `global`, `supplier`, `marketplace`, `user`
4. `scope_id`
5. `period_from`
6. `period_to`
7. `target_value`
8. `current_value`
9. `status`
10. `created_by`
11. `created_at`

### 17.22. Безопасный rollout

Так как scoring может быть спорным, внедрять нужно мягко:

1. Сначала read-only дашборд.
2. Потом snapshots.
3. Потом events.
4. Потом work items read-only.
5. Потом ручное назначение задач.
6. Потом автоматические рекомендации.
7. Потом автозадачи и уведомления.

Важно: не блокировать текущую работу контент-менеджеров, пока scoring не проверен на реальных поставщиках.

### 17.23. Что добавить в улучшенный MVP

Если делать "очень сильный MVP", я бы добавил к разделу 16 еще:

1. `opportunity_score`
2. `data_confidence_score`
3. `next_best_action`
4. `bottleneck`
5. `priority_reasons_json`
6. `data_lineage_json`
7. `regression_count`
8. read-only `work_items`
9. простые targets по поставщику
10. простую ленту supplier health timeline

Так первая версия уже будет отвечать не только "что происходит", но и "где деньги, где риск, что делать сегодня и можно ли верить цифрам".
